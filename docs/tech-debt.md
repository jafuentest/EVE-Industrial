# Tech Debt

---

## Frontend

- [ ] **Add zod validation at API boundaries** — API responses are currently trusted via `as` type assertions (e.g. `camelize(data) as Counters` in `useCounters`). Once page functionality is done, add zod: one schema per response type, derive the TS types via `z.infer`, and replace assertions with `Schema.parse()` so malformed responses throw instead of leaking `undefined` into state.

- [ ] **Sync ESI button has no in-flight state** — rapid clicks fire redundant `POST /api/sync` requests (harmless to ESI thanks to the backend 5-min cache guard) and give the user no feedback that a sync is running. Disable the button while the request is in flight.

- [ ] **`Login.tsx` conflates "not logged in" with "request failed"** — the `GET /api/session` handler only branches on `status === 200`; any other status (including a 500) falls into the same `else` as the expected `401` and just shows the login button with no explanation. Split into three branches — `200` redirect, `401` set `loginUrl`, else set an `error` state and render it — so an actual failure doesn't look like a silent, unexplained login prompt.

## Backend

- [ ] **`annotate` gem is broken on Ruby 3.3** — `annotate` 2.6.5 calls `File.exists?`, removed in Ruby 3.2+, so `bundle exec annotate` crashes and model schema headers must be updated by hand. Successor gem is `annotaterb`.

- [ ] **`User.find_or_register` does not handle bad OAuth code** — `app/models/user.rb`. If EVE SSO returns an invalid or expired `code`, `ESI.authenticate(code)` will raise or return an unexpected response, causing an unhandled exception in `Users::SessionsController#new`. Needs a rescue block that redirects the user back to the login screen with an error message.

- [ ] **Order syncing dominates ESI call volume and can lose orders** — the two competing-order paths in `Order.update_competing_orders` (`app/models/order.rb:66`) account for most of the work a sync does. NPC stations go through `update_region_orders` (`order.rb:99`), which fires one `ESI.fetch_region_orders` per distinct `type_id`; citadels go through `update_citadel_orders` (`order.rb:107`), which pages in an unbounded `loop` until a blank response. For a 3-character account trading ~30 item types, that alone is roughly 90 of the ~120 sequential ESI round-trips in a single `sync_from_esi` (`user.rb:108`). Separately, `User#update_market_orders` (`user.rb:119`) calls `Order.where(character_id:).delete_all` *before* refetching, with no transaction — if the sync dies partway (timeout, ESI 502, worker restart) the character's orders are deleted and never repopulated. Batch or cache the region lookups, bound the citadel pagination, and make the refresh non-destructive: `update_character_orders` already calls `destroy_missing_orders` (`order.rb:78`), so the leading `delete_all` is likely redundant. Note also that `Rails.cache.fetch("esi_sync/#{id}")` only writes its entry after the block returns, so a sync that times out isn't rate-limited on retry and will restart the whole run.

- [ ] **ESI calls within a sync run sequentially** — every fetch is a blocking `Net::HTTP` round-trip, and `sync_from_esi` issues on the order of 120 of them for a modest account — roughly 18s at 150ms each, on a single Puma worker for the whole duration. Most of that work is independent and parallelizable: per-character syncs don't interact, and the per-item region lookups within a character don't either. Wants a bounded thread pool (respecting ESI's rate-limit and error-limit headers rather than fanning out unbounded). Worth pairing with connection reuse — `ESI.parsed_response` opens a fresh `Net::HTTP.start` per call, so a pooled or keep-alive client compounds the gain. Should be attempted after the order-syncing fan-out above is reduced; cutting the call count first makes the concurrency cheaper to reason about.

- [ ] **Missing ESI scopes are not detected** — every time a scope is added to `ESIHelper::SCOPES` (`app/helpers/esi_helper.rb:4`), grants authorized before that point don't include it, and nothing reports the gap. `reauth_required` doesn't cover it: the token refresh still succeeds, the token is just unauthorized for the new endpoint, so `Character#auth_token` never reaches `mark_reauth_required`. ESI answers those calls with a 403 and a JSON error body, and since `ESI.parsed_response` ignores the response status, every caller receives that error body as if it were data and degrades according to whatever guard it happens to have — silently, and differently in each case. The data needed to detect it is already persisted: `scopes` is captured from the grant on both models (`character.rb:30`, `user.rb:66`) and never overwritten on refresh, so `ESIHelper::SCOPES - scopes.to_s.split` is sufficient. Should be a warning only — never gate ESI requests on it — surfaced as a field on the characters payload for the Settings page, and ideally a notification when scopes change. Keep it separate from `reauth_required`, which is a hard failure. Needs a shared home: `User` and `Character` both carry `scopes` and tokens, and each controller defines its own `character_json`.
